### 1.2 数据流全景

```
视频文件(D:\video_data\videos\)
        |
        +--> Express scanVideoDirectory() 每30秒自动扫描
        |      +- 子目录 = 短剧 (dramas 表)
        |      +- mp4 文件按名排序 = 剧集 (episodes 表)
        |      +- pictures/ 前缀匹配 = 封面
        |
        +--> AI 分析引擎 watcher.py 后台监控
               |
               +- 新视频检测 -> run_analysis.py --video-url
               |
               +- 双通道抽帧 -+- 通道1: ffmpeg scene detection -> 30帧
               |              +- 通道2: ASR 说话人时间点 -> 精准帧
               |
               +- VL 多模态分析 (逐帧, 帧缓存去重)
               |     +- scene_description (场景描述)
               |     +- characters (在场人物)
               |     +- key_event (关键事件)
               |     +- expression_score (表情感染力 0-5)
               |
               +- 音频分析 (独立容错, 失败不阻断)
               |     +- fsmn-vad 语音活动检测
               |     +- paraformer-zh 逐片段 ASR 识别
               |     +- CAMPPlus 说话人分离
               |
               +- 时间轴融合 EpisodeTimeline.build()
               |     +- 1s 网格对齐音视信号
               |     +- 四维高光公式: 0.30x用词 + 0.25x表情 + 0.25x剧情 + 0.20x音画
               |     +- _extract_highlights(min_score=0.5, merge_gap=0.5s, max_dur=60s)
               |
               +- LLM 结构化提取 (人物关系图谱 + 剧情转折)
               |     +- 注入 ViewerContext 跨集上下文
               |
               +- POST /internal/highlights
                     +- Redis: highlight:{episode_id} (1h TTL)
                     +- lowdb: drama.json -> highlights[] (持久化)

浏览器 GET /api/episodes/:id/highlights
      +- 优先 Redis -> 命中即返回
      +- fallback lowdb -> 兜底保证可用
```

## 2. 核心模块技术选型与理由

### 2.1 客户端 / 前端

| 技术 | 版本 | 选型理由 |
|------|------|----------|
| **React** | 18 | 生态成熟，Hooks 模式适合中型 SPA；函数组件 + Context 管理认证状态，无需引入 Redux 等重量状态库 |
| **TypeScript** | 5.3 | strict 模式 + noUnusedLocals/noUnusedParameters，编译期拦截类型错误；给 API 响应定义接口类型，前后端契约可验证 |
| **Vite** | 5 | 毫秒级 HMR，开发体验优于 webpack；代理配置简洁（/api -> localhost:3001），无需 CORS 调试 |
| **TailwindCSS** | 3 | 原子化 CSS，暗色主题用 CSS 变量实现，不引入组件库避免体积膨胀；与 @tailwindcss/vite 4.x 共存 |
| **HLS.js** | 1.4 | 自适应码流，自动降级原生 video；支持 m3u8 和 mp4 双模式；播放器状态机 8 状态覆盖加载/缓冲/错误/续播 |

### 2.2 后端

| 技术 | 版本 | 选型理由 |
|------|------|----------|
| **Express** | 4 | Node.js 最成熟的 HTTP 框架，中间件生态丰富；单文件 800 行足够覆盖全部路由，避免过度拆分 |
| **JWT + bcrypt** | — | 双 Token 机制：Access Token 2h + Refresh Token 30d；bcrypt 哈希存储密码，不存明文 |
| **helmet + CORS** | 7 | helmet 设置安全头（CSP/X-Frame 等），CORS 全局允许局域网访问 |
| **Range 流媒体** | — | Node.js fs.createReadStream + Accept-Ranges 头，支持 206 Partial Content，拖动进度条不重新加载全片 |

### 2.3 数据库

| 技术 | 选型理由 |
|------|----------|
| **lowdb 7** | JSON 文件数据库，零依赖零配置，数据量 < 10MB 时性能足够；dramas/episodes 每次扫描全量重建，highlights/play_history/users 持久化保留；适合单机局域网部署，无需独立数据库进程 |
| **Redis 6+** | 可选缓存层：session(30d TTL)、video cache(10min TTL)、highlights(1h TTL)；ioredis 客户端支持自动重连和优雅降级 |
| **混合策略** | Redis 可用时双写（Redis + lowdb），不可用时纯 lowdb；GET 先查 Redis 热数据，miss 后 fallback lowdb，保证服务零中断 |

### 2.4 AI 模型

| 模型/能力 | 供应商 | 选型理由 |
|-----------|--------|----------|
| **豆包 VL Pro 32K** | 火山方舟 Ark | 多模态理解，OpenAI 兼容 API；单帧 0.012 元，帧缓存命中后零成本；32K 上下文可容纳长 prompt + 多帧批处理 |
| **豆包 LLM** | 火山方舟 Ark | 结构化提取（人物/关系/转折），同供应商简化 API 密钥管理 |
| **FunASR 1.3.9** | 阿里达摩院 | 中文 ASR 最优方案，fsmn-vad + paraformer-zh + CAMPPlus 三模型管线；独立容错加载，失败跳过不阻断整体流程 |
| **ffmpeg** | 系统工具 | 场景切换检测 (select='gt(scene,0.3)')、精准时间戳抽帧、视频时长提取 |

## 3. 大模型 / AI 能力使用说明

### 3.1 模型调用架构

API 网关: https://ark.cn-beijing.volces.com/api/v3
认证方式: Bearer Token (DOUBAO_API_KEY 环境变量)
调用模式: OpenAI 兼容格式 (openai Python SDK)
密钥管理: api_config.py (项目根目录, 已入 .gitignore, 项目内 sys.path 动态加载)

**两个模型端点：**

| 用途 | 模型 | 环境变量 | 调用方式 |
|------|------|----------|----------|
| 视觉帧分析 | doubao-1.5-vision-pro-32k | DOUBAO_EP | openai.chat.completions.create(model=Config.DOUBAO_VL_MODEL) |
| 结构化提取 | doubao-1.5-pro-32k (LLM) | DOUBAO_EP | openai.chat.completions.create(model=Config.DOUBAO_LLM_MODEL) |

### 3.2 LLM 调用场景总览

| 场景 | 模型 | 调用频率 | 输入 | 输出 | 缓存 |
|------|------|----------|------|------|------|
| 帧场景描述 | VL | 30+ 次/集 | base64 帧图片 + prompt | 英文 JSON (scene_description, characters, key_event) | SHA256:model:tag |
| 说话人识别 | VL | N_spk x 1 次/集 | 说话人时间点 +/-1s 精准帧 | 角色外观描述 | SHA256:model:speaker |
| 表情强度打分 | VL | N_spk x 1 次/集 | 说话人帧 | expression_score 0-5 | SHA256:model:expression |
| 画面表现强度 | VL | 30 次/集 | 场景帧 | visual_intensity 0-5 | 帧缓存共享 |
| 结构化提取 | LLM | 1 次/集 | 时间轴摘要 + ViewerContext | 人物/关系/场景/转折 key_scenes | 无缓存 |

### 3.3 Prompt 设计

**VL 帧分析 Prompt**

```
Analyze this frame from a Chinese short drama. Return JSON:
{
  "scene_description": "describe the setting, lighting, mood",
  "characters": ["name1", "name2"],
  "key_event": "what is happening in this scene",
  "visual_intensity": 0-5 scale of dramatic intensity
}
```

> 强制英文键名输出，避免中英文键不匹配导致高光得分全部为 0 的问题。

**LLM 结构化提取 Prompt**

```
Analyze the timeline of a Chinese short drama episode.
{viewer_context}

Timeline: {timeline_summary}

Detect narrative turning points using:
1. Power dynamics shift
2. Secret/truth revealed
3. Major conflict escalation/de-escalation
4. Character betrayal or alliance
5. Life-threatening situation
6. Emotional climax

Return JSON:
- characters: [{name, role, traits}]
- relationships: [{char1, char2, relation_type, intensity}]
- key_scenes: [{start_sec, end_sec, description, twist_type}]
- summary: 1-2 sentence episode summary
```

> viewer_context 由 ViewerContext 类管理，跨集累积角色和关键事件，模拟真实观众知识增量。

### 3.4 帧缓存去重策略

```
缓存键结构: SHA256(image_bytes)[:16] + ":" + model_name + ":" + tag
tag 取值: "scene" | "speaker" | "expression"
存储位置: server/analysis/cache/frame_cache.json

不同 tag 独立缓存 -> 同一帧的场景分析、说话人识别、表情打分不互相覆盖
每集结束 flush 内存 dict -> gc.collect() 释放
跨集共享缓存文件 -> 重复帧零 API 调用
```

## 4. 工程难点与解决方案

### 4.1 音频分析管线不稳定 -> 分级容错降级

**问题描述**

FunASR 三模型管线 (fsmn-vad -> paraformer-zh -> CAMPPlus) 对环境依赖敏感：pytorch_wpe、whisper 等模块缺失导致部分模型加载失败；ASR 全片一次识别导致所有 VAD 片段返回相同文本；CAMPPlus 说话人分离输出格式与预期不符。

**解决方案 — 三级容错**

- **Level 1: 独立模型加载** — 每个模型用独立 try/except 包裹，失败时打印警告，不抛异常
- **Level 2: 逐片段 ASR** — 不再一次传入全片音频，改为遍历 VAD 片段逐条裁剪音频后独立识别，文本不再重复
- **Level 3: 全模块降级** — audio_analyzer 整体失败时返回空 segments，时间轴融合跳过音频层，高光公式退化为纯视觉三维，分析流程不崩溃

**效果**: 音频不可用时，视觉维度和叙事维度仍正常工作；ASR 文本现已正确对应到 VAD 片段。

### 4.2 高光区间链式合并导致超长 -> 参数约束 + 硬截断

**问题描述**

_extract_highlights 合并阶段：min_score=0.15 阈值过低，merge_gap=10s 间隙过宽。一旦某集音频情绪分覆盖大面积时间范围（如天下第一纨绔 ep3 有 180s+ 对话），大量 1s 格子过线，合并链贯穿全片，产出 337s、200s 等超长"高光区间"。

**解决方案 — 双保险**

- **参数收紧**: min_score 0.15->0.5（过滤低能量伪高光），merge_gap 10.0->0.5（只合严格紧邻片段）
- **硬截断**: max_duration=60s，超长区间居中截断为 +/-30s 窗口，在 _extract_highlights 和 _sync_highlights_to_backend 两处同时生效

**效果**: 8 个超长区间全部截为 60s 居中窗口，后续新分析不再产出超长区间。

### 4.3 VL 缓存键撞车 + 中英文键漂移 -> 分级键 + Prompt 规范化

**问题描述**

早期版本帧缓存键仅 SHA256[:16]:model，未区分分析目的 (scene/speaker/expression)，导致说话人识别结果覆盖场景描述；VL Prompt 返回中文键名与代码期望英文键名不匹配，所有高光得分为 0。

**解决方案**

- **三级缓存键**: hash:model -> hash:model:tag，tag 区分 scene/speaker/expression，不同分析目的独立缓存互不覆盖
- **Prompt 规范化**: VL prompt 明确标注 Return JSON with English keys only，清空旧缓存（中文键条目全部删除）
- **运行时验证**: 修改缓存键后自动清空旧格式缓存文件，打印缓存命中/未命中计数

### 4.4 视频帧截取与缓存命中优化 -> 双通道抽帧 + 三级缓存键

**问题描述**

单通道均匀间隔抽帧存在两个核心矛盾：① 固定间隔（如每 5s 一帧）可能错过高光时刻的精准画面；② 不同分析目的（场景理解 vs 说话人识别 vs 表情分析）对帧的位置需求不同，但早期共用一个帧缓存键，导致不同分析结果相互覆盖。

**解决方案**

**抽帧层 — 双通道互补**

- **通道1: 场景检测抽帧（30帧/集）**
  ffmpeg `select='gt(scene,0.3)'` 基于像素差异检测场景切换点，产出的帧天然落在剧情转折位置，构成"剧情骨架"
  若场景检测产出 < 5 帧，fallback 到均匀间隔抽帧，避免静态场景集帧数不足

- **通道2: ASR 说话人时间点精准抽帧**
  从音频分析获取每个说话人片段的起止时间，在 spk 时间点 +/-1s 处精准截取，确保"谁在说话"时有对应画面
  该通道专门服务于角色锚定和表情强度分析，与场景检测帧互补

- **时间戳精准截取**: `extract_frame_at_timestamp(video_path, timestamp)` 通过 ffmpeg `-ss` 精确定位，误差 < 0.1s

**缓存层 — 三级键去重**

- 缓存键结构: `SHA256(image_bytes)[:16] + ":" + model_name + ":" + tag`
- tag 取值场景化：`"scene"`（场景描述）、`"speaker"`（说话人识别）、`"expression"`（表情打分）
- 不同 tag 独立缓存，同一帧用于三种分析目的时各自缓存不覆盖
- 跨集共享缓存文件 `frame_cache.json`，场景复用帧命中后零 API 调用
- 每集结束 `flush` 内存 dict + `gc.collect()` 释放，避免 30 帧 VL 分析后内存持续增长

**效果**

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 角色帧覆盖率 | 场景帧中人物不全，约 40% 缺失 | ASR 精准帧锚定，提升至 85%+ |
| 缓存命中率 | 跨集复用率约 15%（键不区分 tag） | 跨集复用率 40%+，命中帧零 API 成本 |
| 缓存覆盖 bug | 说话人识别结果覆盖场景描述 | 三级键完全隔离，零覆盖 |

*文档结束*
